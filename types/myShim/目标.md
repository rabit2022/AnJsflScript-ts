# 项目目标

## ts 重构AnJsflScript代码

### AnJsflScript代码比较复杂,对于类的支持有多次变更

1. prototype 实现
2. Class.js,overload-js等第三方库的实现
3. babel的转译代码
4. 最后的ts实现

* 因此,ts 重构 会统一这些实现,不再关心类的问题

### 代码提示问题

AnJsflScript混合了js与ts 代码,导致代码提示不准确,部分代码提示报错,但是能够运行
ts 重构 ,代码提示更加准确,可以减少.d.ts的维护

### xjsfl问题

xjsfl代码老旧,但是可以正常运行
试图重构为ts代码,as代码将不再收录

### webpack打包

AnJsflScript尝试webpack打包为单个文件,但是由于babel生成了太多的兼容代码,使得运行效率低下
ts 生成的兼容代码更少,并去掉webpack打包部分
不再打包为一个文件,这会导致jsfl执行缓慢

#### 注意

不要试图打包为一个文件,因为不是所有的模块都支持 "树摇优化",webpack似乎只有es6 import 的支持最好 ,commonjs的代码,往往是全部打包进来
那么,就会出现一个问题,一个文件有5000行代码,jsfl运行时非常慢
即使是es6 import,经过了"树摇优化",依旧可能有3000行代码,例如lodash-es6,内部模块化,导致即使用了一个方法,也会打包3000行代码
尽量导入模块,因为requirejs是按需加载的,加载一次后的模块会一直存在于requirejs内部.如果打包为一个文件,就会出现每次运行require时,都会再次加载同一批对象,运行结束释放掉,造成资源浪费,而且可以重用的模块也没有缓存

### console模块

AnJsflScript console模块 兼容了太多的东西,比较臃肿
精简console模块,职责分工

### 重构问题

AnJsflScript 混合了js与ts 代码,导致重构难,引用难以分辨,为了兼容性做了depredicate标记
将会彻底的去除废弃代码,因此当前项目与AnJsflScript不兼容

### 版本号文件夹的问题

AnJsflScript 第三方库的文件夹 保留了版本号,这是不必要的,将会去除版本号

### 制作插件UI问题

不打算制作,因为时间有限,精力有限
UI的制作投入的时间成本比较高,没有制作的意愿
社区反馈过少,没有制作的意愿

#### 插件UI的方向

1. 传统的方式:as+swf,做flash动画,可以顺手做,但是比较消耗时间,as代码与js同源,代码简单,但是并没有好的代码编辑器,效率相对低.总之,需要投入的时间成本比较高
2. CEP (Common Extensibility Platform):HTML/CSS/JS制作UI,在Adobe官方的表格中,可以看到,Animate是支持的.好处是可以用AI快速完成,AI相当擅长前端的制作,有很多的参考示例,关于Adobe的其他软件的扩展

### jsfl扩展难度问题

总体来说,比较简单
市面上的插件功能,逻辑都是同一套

```markdown
1. 手动实现
2. 对应到代码
```

因此,非常直观,只要有他的效果,试着手动实现,就会写代码
而且,可以查看"历史"面板,手动实现的时候,可以直接拿到api,非常的快速

可以说,市场上的插件,功能都比较简单,真正硬核的只有很少的几个

例如 "丝滑飘动","复制动作"等功能,需要查询文档,对文档有深度的理解
